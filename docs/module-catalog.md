# Module Catalogue — `odoo-platform` → `bct`

Inventory and grouping of the 154 custom Odoo 19 addons in
`github.com/sarangrumah/odoo-platform`, assessed for import into this repository.

This document is the curated reading of the data. The full per-module row set —
all 154 modules, 23 columns — is `module-catalog.csv`, regenerated by
`tools/module_inventory.py` in the platform repo:

```
python tools/module_diff.py --hub <platform>/addons --vertical bct=<bct>/addons \
    --out diff.md --json diff.json
python tools/module_inventory.py --diff-json diff.json --addons <platform>/addons \
    --target-addons <bct>/addons \
    --classification <bct>/addons/custom_pdp_core/data/pdp.field.classification.csv \
    --odoo-core "C:/Program Files/Odoo 19.0.20251029/server" \
    --out-json catalog.json --out-csv catalog.csv --out-md catalog.md
```

Every number below was measured, not quoted. The platform's own docs are stale by
20–90 modules (`architecture.md` says `ee_gap` has 78; it has 101).

---

## 1. What is being catalogued

**154 modules · 239,321 LOC · 600 models owned · 21,000+ fields.**
For comparison, this repository's `addons/` today is 5 modules and ~7,700 lines.

Licensing is uniform: **153 LGPL-3**, one AGPL-3 (`partner_firstname`, a vendored
OCA module nothing depends on). The platform repo has **no `LICENSE` file at its
root** — the licence is asserted only in one README line. That should be fixed
before anything is redistributed.

## 2. The five axes

Tier, capability tags and industry-pack membership already exist in the platform's
own code and are reused rather than reinvented — `architecture.md` § *Module tiers*
is explicit that **the `addons/<group>/` folder decides the tier, not the manifest
category**. Two axes are added here: measured maturity, and a disposition.

### Tier — decides load order

`_vendor → core → control_plane → compliance → ee_gap → operations → verticals → _tenants`

That is the platform's `addons_path` order, and it is also a safe import order.

| `verticals` | 14 | One industry (PPOB ×12, F&B, template) |

| `compliance` | 9 | Every Indonesian tenant |

coupling: it ships that customer's records to every tenant that installs the

## 3. This is not a pick-and-choose menu

`custom_core` has **103 dependents**, `custom_pdp_audit` **77**, `custom_pdp_core`
**20**, `custom_ai_bridge` **15**. Modules sit on topological layers L0–L9. Any
import starts with the foundation or it does not start.

Two wiring differences must be settled before the first module lands:

- **`addons_path`.** This repo uses a flat 2-entry path; the platform uses a nested
  8-entry one. With a flat path, two directories of the same name silently shadow
  each other.
- **`server_wide_modules`.** This repo loads `base,web`. **Nine modules** need
  `queue_job` loaded server-wide, not merely installed: `custom_retail_import`,
  `custom_retail_import_api`, `custom_whatsapp`, `custom_esb_connector`,
  `custom_brd_analyzer`, `custom_fnb_stock_ops`, `custom_email_marketing`,
  `custom_finance_portal_sap`, `custom_receipt_async`.

There is also **no delivery path for `addons/` outside dev**: the bind mount exists
only in `docker-compose.dev.yml`, and neither the base compose file nor `cd.yml`
mentions addons at all.

## 5. Collisions with the five addons already here

The addons in this repo are original greenfield implementations that happen to
share directory names with entirely different modules upstream.

| | This repo | Platform | Verdict |
|---|---|---|---|
| `custom_pdp_core` | `pdp.field.classification`, `depends: ["base"]`, 740-row CSV seed | `pdp.classification` + `ir.model.fields` extension, `depends: ["custom_core"]` | **Directory name collides** |
| `custom_pdp_masking` | `pdp.masking.rule`, `pdp_hash.py`, `pdp_export.py` | `pdp.masking`, `custom.pdp.field.registry`, discovery wizard | **Name collides, and so does a model** |
| `custom_ppob` | `ppob.*`, 353 lines, warehouse fixture | `custom.ppob.*`, 12 modules, transaction engine | No directory collision; semantic overlap |

**`pdp.masked.mixin` is defined in both, differently.** They cannot be installed in
one database. This repo's version is the newer of the two (2026-08-31 vs 2026-08-04)
and carries the warehouse hashing the CDC loader's known-answer test pins; the
platform's carries a field registry and discovery wizard this one lacks. They are
**divergent, not one superseding the other** — this needs an explicit merge, not a
choice of directory.

## 6. Duplication found inside the platform

There is **not one literal `_name` collision** between two platform modules. Every
apparent duplicate is Odoo's legitimate `_name` + `_inherit` mixin idiom. All the
duplication is **semantic**: the same domain modelled twice under different names.

| Pri | Finding | Recommendation |
|---|---|---|
| P0 | **Two parallel PPh withholding engines, with no dependency between them.** `custom_pph_witholding` (626 lines — computes a number, writes a log row) vs `custom_tax_id` (1,613 lines — posts and unwinds real GL entries, with a Hutang Pajak account constraint). Same PPh-type enumeration. | Keep `custom_tax_id`; retire `custom_pph_witholding`. Two live consumers: `custom_pdp_masking`, `custom_ppob_commission`. |
| P0 | **Two e-Faktur exports covering the same 7 document types.** `custom_coretax` emits XML against `urn:djp:coretax:v1`, a placeholder namespace with no bundled XSD — `custom_coretax_export`'s own manifest says so. | Retire the XML wizard; keep `custom_coretax` for `custom.coretax.config`, the adapter base and NSFP fields. **And compare both against core `l10n_id_efaktur_coretax` — see §7.** |
| P0 | **The same 10-digit chart of accounts shipped twice.** `_tenants/custom_arka_aim_seed/data/account.account.csv` (548 codes) vs `l10n_erajaya` (534) — **534 identical**. | Keep the chart template; drop the tenant CSV payload. |
| P1 | Bukti Potong modelled **three times**: `custom.coretax.bukti.potong`, `custom.bupot.unifikasi(+line)`, `account.move.withholding.line`. The export wizard reads only the third. | Consolidate onto one. |
| P1 | `l10n_id_psak_custom` is `auto_install: True` **and** hard-depended by `custom_accounting_full` → every accounting tenant is forced onto the PSAK chart. | Make the dependency soft. |
| P2 | Bank-statement auto-matching written twice: `custom.reconcile.rule` vs `_get_auto_match_candidate()`, in modules that do not depend on each other. | Merge the automatic path; keep the manual wizard. |
| P3 | `custom_wms_docs` depends on `custom_barcode` yet ignores its `custom.label.template` engine and ships its own label wizard. | Reuse the engine. |

**Clusters that are already clean — leave them alone:** rental (3 of 4 extensions
define no new models at all — the best-layered cluster in the repo), WMS (11 modules
plus barcode and HHT; `custom_wms_sap_slotting` *inherits* the putaway engine rather
than reimplementing it), and PPOB (12 modules, root `custom_ppob_core`, every model
singly owned).

## 10. Separating Finance from Accounting in the menu

Odoo CE has **one** root application here: `account.menu_finance`, labelled
**"Invoicing"**. Accounting is not a separate app — it is the `menu_finance_entries`
submenu *inside* Invoicing. Custom modules add **75 more menu items** to that same
root (`custom_accounting_reports` 42, `custom_accounting_full` 16,
`custom_accounting_asset` 8, and others).

They can be separated without touching core code, via a new module that:

- declares a new **"Accounting"** root application;
- re-parents to it — by XML-ID override, a standard Odoo technique —
  `menu_finance_entries` (Transactions, Closing), `account_audit_menu` (Review), the
  accounting reports, and the custom consolidation / assets / recurring / reconcile /
  deferred / batch-payment menus;
- leaves **"Invoicing"** holding the document flow: Dashboard, Customers, Vendors,
  and invoice-level configuration;
- gates each root by group — Accounting on `account.group_account_readonly` /
  `group_account_manager`, Invoicing on `account.group_account_invoice`.

⚠️ Re-parenting a core menu record applies to every user. `custom_home_console`
groups applications on its landing page via `HOME_CONSOLE_GROUPS` and must be
updated in step.

## 12. What the import actually did

The catalogue above describes the source suite. This section records the state of
this repository after the import ran, and the things that only surfaced by
installing the modules rather than reading them.

**149 of the 154 source modules were imported**, into `addons/<group>/`. The five
modules written here keep their existing paths at the root of `addons/`, so the
`addons_path` lists the bare mount first and the eight group directories after it.
Together with one new module written here (`custom_accounting_menu`), the tree
holds 155 modules and every declared dependency resolves.

**332 modules install and the registry loads.** Two of the imported modules are
deliberately not in the install set:

| Module | Why it is not installed |
|---|---|
| `custom_arka_aim_seed` | Its own manifest says "INSTALL ONLY ON THE erp_dev_aimarka TENANT DB". Its `post_init_hook` changes the company currency, which fails on any database that already has journal entries. It stays in `_tenants/` where a tenant deployment can install it. |
| `custom_storefront_api` | It redefines `res.partner.phone`, `street`, `street2` and `zip` as **non-stored** computed fields backed by encrypted columns. Its own docstring calls this a trade-off and notes the fields stop being searchable. Here it also silently empties four columns the CDC pipeline replicates, so the warehouse received NULL for every partner's phone and address. This deployment already protects that data — the policy classifies all four as `personal`, so they are HMAC-digested during load and never land as plaintext. The module has zero dependents. |

The second one is worth generalising: **an addon that changes a field from stored
to computed silently breaks logical replication of that column.** Nothing errors;
the warehouse just starts receiving NULL. It was caught by
`tests/test_01_live_sync.py`, which asserts the landed digest matches the source
value, not merely that a row arrived.

### Client naming

No customer name remains anywhere in `addons/` — not in prose, not in module
directories, model names, field names, XML IDs or Python class names. The scrub
runs inside the import pipeline, so re-running the import reproduces it rather
than undoing it.

| Was | Is | Scale |
|---|---|---|
| `erajaya` | the chart it names (`10-digit chart`, `l10n_id_coa_10d`) | 725 occurrences |
| `levis` | `retail` | 129 files; 12 models, 1 field on `account.move` |
| `eraspace` | `pos` | 44 files; 6 models, 2 fields |
| `vaspmo` | `pmo` | 45 files; 2 models |
| `arka` / `aim` / `arkaaim` | `tenant` | 90 files; 7 module directories |
| `erafone` | `mobile` | brand-seed record |

Three rules were needed, not one, and each was found by something breaking:

- **Letter boundaries**, so `claim` is not an ARKA-AIM sighting and `we aim to`
  survives. A bare `` is not enough: `erajaya_2104300001` is one word to ``,
  and that XML-ID prefix is exactly the coupling worth removing.
- **CamelCase**, matched on the following capital. `LevisCategReclass` has a letter
  straight after the name, so the boundary rule that protects prose also blocks the
  class name.
- **UPPERCASE identifiers** (`AIM_COMPANY`), matched on the trailing underscore.
  An underscore is not a letter, so the prose rule fired and produced
  `the tenant_COMPANY` — a `SyntaxError` that only appeared when Odoo imported the
  module. `--verify-python` now compiles all 1,701 imported files and would have
  caught it in a second.

### The database migration

Renaming in the source is half the job. The names are also in
`ir_module_module.name`, `ir_model.model` and the tables behind it,
`ir_model_fields.name` and its columns, and 655 `ir_model_data` rows. Odoo renames
none of those on upgrade: it would treat every renamed model as new, leave the old
tables orphaned and the old module installed.

`scripts/migrate-client-renames.py` does the rename in the database. It derives the
new names by importing the same substitution table the import script uses, so the
two cannot drift. Every statement is guarded on the old name still being present, so
it is idempotent and a second run is a no-op.

For this database the migration was **not strictly required** — every affected table
held zero rows, seed rows the module recreates, or a derived SQL view. It was
written and run anyway, because a tenant database with real data needs exactly this
and would otherwise have no path forward.

Four things it had to learn:

| Problem | Why |
|---|---|
| `custom_pdp_core → custom_pdp_taxonomy` must NOT be replayed | That rename resolves a name *collision* at import time. In the database `custom_pdp_core` is this repo's own module and is already correct; replaying it renames it onto the taxonomy module and Postgres rejects it on the unique index. Import-time renames and de-branding renames are now separate sets. |
| `ir_act_server.model_name` does not exist in Odoo 19 | The reference-column list is written against a schema, so it is filtered against `information_schema` rather than trusted. A wrong entry is skipped, not fatal. |
| Many2many join tables | They are named `<model_a>_<model_b>_rel`, so a model's table name is a *prefix*, not the whole name. Renaming only exact matches left `levis_categ_reclass_product_template_rel` behind, and Odoo would have created a second, empty join table beside it. |
| Ordering between passes | The model pass rewrites part of a field's XML ID, which then no longer matches what the XML-ID pass collected. Because every statement is guarded, a second run converges — which is what idempotency is for. |

### Landing-zone orphans

The rename exposed the other half of "`gen-raw-ddl` only ever adds columns": a
source column that is renamed or removed leaves its old column in `raw.*`, with no
policy row. Contract 01 makes an unclassified landed column a hard failure, so
`tests/test_04_masking.py` failed on twelve of them.

`gen-raw-ddl` now prunes, under two rules it will not break:

- An **empty** orphan is dropped. If dbt's `staging`/`marts` views depend on it the
  drop cascades, because dbt rebuilds those from source on the next run. A
  dependant anywhere else is somebody's object, and the prune refuses.
- An orphan **with data** is never dropped automatically. It is reported with the
  statement to run and the command exits non-zero, so the pipeline stops rather
  than continuing in a state contract 01 forbids.

Eleven were empty. One was not: `raw.res_partner.custom_phone_enc` held 8 rows of
Fernet ciphertext written while `custom_storefront_api` was installed. It was
dropped deliberately, not automatically — nothing downstream can read it (no model,
no policy row, no key holder), and the phone it encrypts already lands correctly as
an HMAC digest in `raw.res_partner.phone`.
